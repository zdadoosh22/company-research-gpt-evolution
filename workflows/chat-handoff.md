# Chat / Work handoff protocol

User-requested standing workflow, 9 October 2026. This implements the explicit handoff instructions; it does not alter analytical methodology 1.0.0, approve a company or enable trading.

## Roles and access

The ordinary planning/review companion is **Company Research - review and planning**, a separate ChatGPT project. Chat develops criticism, decisions, acceptance criteria and bounded Work assignments. Work inspects authoritative Windows files, captures evidence, performs authorised integration/verification, records dispositions and prepares handoffs. Neither project placement nor a repository URL grants Chat access to the local folder or Work conversation.

The dedicated private repository is `zdadoosh22/company-research-work`, descriptive title **Company research (work)**, connected to the existing Company research 2 folder. Never reuse or modify Trading Shadow Agent, trading-shadow-agent or Ai-research-hub. Historical reference repositories remain read-only and their histories/credentials are not imported.

## Timing and scope

At the next sensible checkpoint where substantial planning or criticism would help, first finish a coherent implementation/research/verification step. Do not interrupt that step just to transfer context. Recover actual goal status. A handoff request alone does not pause, replace or create a goal. Respect an explicit retirement or pause; do not resume old continuation instructions automatically.

Use `validation/chat-handoff-YYYY-MM-DD-<scope>/`, with a purpose/date/version and source manifest. Never overwrite authoritative originals or a previous frozen package. If an existing directory is already published, use a new dated/revision directory. Copy or excerpt only material needed for the specific review; do not duplicate the whole project or rerun completed audits merely to produce a package.

## Required package content

1. A specific task/question for Chat, a dated baseline, relevant versions/hashes, verified repository URL/branch/commit and the exact files to read.
2. Actual completed work and verification evidence, with test scope, dates and limitations. Distinguish engineering checks, analytical review, research approval, portfolio decisions and execution.
3. Unresolved defects, evidence gaps and uncertainty, current partial/awaiting-review/approval states, interrupted operations, and exact next decisions.
4. Explicit supersession: identify historical status/continuation/instruction copies that must no longer govern current work. Newer bytes alone do not imply new approval. Include full replacement reference text when standing instructions or approved methodology changed.
5. Relevant changed document contents, source passages or labelled summaries, formulas/calculations, outputs and necessary code interfaces. Windows paths and hashes alone do not deliver evidence. Preserve raw/derived/source-authentication distinctions.
6. A bounded exclusion register. Never upload credentials, private account records or raw operational databases/state. Supply a labelled sanitised projection if those records contain necessary acceptance facts. Identify excluded material Chat cannot inspect and its verification limits.
7. Exact upload files, a short ready-to-send Chat message, and a separate repository-access challenge. Do not claim the Chat GitHub plugin works until Chat actually retrieves the pinned files.

## Versioning and verification

Keep source bytes intact across Git check-in/check-out; publication hashes remain meaningful. Verify the local project-specific Git root, staged paths/privacy controls, private standalone repository identity, pushed branch/commit and uploaded tree/content. A local credential/API verification proves upload, not Chat access. Avoid a self-referential commit claim: a committed package may bind the verified research baseline commit; its final publishing commit belongs in a separate local upload-verification record and ready-to-send message.

Chat should explicitly use its GitHub plugin, retrieve the named files at the supplied full commit, and report a non-sensitive repository identity challenge plus its retrieved sources. If access or revision pinning fails, state that failure and use only explicitly attached copies with their manifest. Do not fabricate access from the prompt, browse a private URL anonymously, or use another repository as a substitute.

## Return assignment

Ask Chat to recommend a normal message or /goal and give one ready-to-send Work prompt. Use a normal message when inspection or a consequential decision must resolve uncertainty first. A /goal needs a defined scope, verifiable endpoint and appropriate sustained work. A completed stage may end with verified artifacts and a prepared handoff; avoid open-ended project-wide confidence/growth objectives.

Before execution, Work checks the recommendation against current files, actual active operations/goals and existing authority. Resolve stale assumptions and scope conflicts, preserve historical evidence, and do not automatically start new development or repeat closed reviews. Chat's proposed instruction/methodology changes remain proposals until actually approved and recorded. No paid service, account connection, broker execution or increased capital is inferred from a handoff or a /goal.
